## 1. Обзор

### 1.1 Цель

Разработать AI Operating System (osaI) на базе форка OpenClaw — open-source personal AI assistant (100k+ GitHub stars,
MIT license). osaI расширяет OpenClaw от персонального ассистента до полноценного AI-слоя управления системой: файлы,
браузер, shell, API, приложения, мессенджеры, desktop-интеграция.

### 1.2 Контекст

OpenClaw — реальный, активно развивающийся проект (запуск ноябрь 2025, 100k+ звёзд, 500+ контрибьюторов, спонсорство
OpenAI и Vercel). Он уже решает 80% задач персонального AI-ассистента. Вместо reimplement с нуля, мы форкаем OpenClaw и
расширяем его до AI OS.

### 1.3 Что наследуется от OpenClaw

| Компонент         | Описание                                          |
|-------------------|---------------------------------------------------|
| Gateway           | WebSocket control plane (ws://127.0.0.1:18789)    |
| Pi Agent Runtime  | RPC-режим с tool streaming + block streaming      |
| Skills System     | SKILL.md формат, bundled/managed/workspace skills |
| Session Model     | Main session + изолированные group sessions       |
| Activation Modes  | always, mention, wake word, passive               |
| Docker Sandboxing | Контейнеры для non-main сессий                    |
| Model Failover    | Цепочка провайдеров, auth profile rotation        |
| Canvas / A2UI     | Agent-driven визуальное рабочее пространство      |

| Voice             | Wake word + Talk Mode                             |
| ClawHub           | Registry для managed skills                       |

## 3. Ядро агента (Agent Core)

### 3.1 Agent Loop

osaI использует agent loop OpenClaw без изменений:

```
INTAKE → CONTEXT ASSEMBLY → MODEL INFERENCE → TOOL EXECUTION → STREAMING → PERSISTENCE
    ↑                                                              │
    └────────────────────── tool_use loop (при необходимости) ──────┘
```

#### 3.3.2 Модель данных чата

```typescript
interface Chat {
  id: string;
  name: string;                   // Название чата
  description: string;            // Описание
  tags: string[];                 // Теги для группировки
  icon: string;                   // Иконка (emoji или кастомная)
  color: string;                  // Цвет для визуальной идентификации
  channel: "cli" | "telegram" | "web" | "whatsapp" | "discord";
  channelMetadata?: {
    telegramChatId?: string;
    telegramMirrorChatId?: string;
  };
  createdAt: Date;
  updatedAt: Date;
  isActive: boolean;
}
```

#### 3.3.3 SQLite схема

```sql
CREATE TABLE chats
(
    id              TEXT PRIMARY KEY,
    name            TEXT NOT NULL,
    description     TEXT           DEFAULT '',
    tags            TEXT,              -- JSON array
    icon            TEXT           DEFAULT '💬',
    color           TEXT           DEFAULT '#6366f1',
    channel         TEXT NOT NULL DEFAULT 'cli',
    channel_metadata TEXT,              -- JSON
    is_active       INTEGER       DEFAULT 1,
    created_at      TEXT NOT NULL DEFAULT (datetime('now')),
    updated_at      TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE TABLE chat_messages
(
    id              TEXT PRIMARY KEY,
    chat_id         TEXT NOT NULL REFERENCES chats (id),
    role            TEXT NOT NULL,      -- "user", "assistant", "system", "tool"
    content         TEXT NOT NULL,
    tool_calls      TEXT,               -- JSON (tool call results)
    metadata        TEXT,               -- JSON (model, tokens, etc.)
    created_at      TEXT NOT NULL DEFAULT (datetime('now'))
);

CREATE INDEX idx_chat_messages_chat_id ON chat_messages (chat_id, created_at);
```

#### 3.3.4 Правила мультичатов

- **Лимит**: до 20 активных чатов одновременно
- **Изоляция**: каждый чат имеет свою историю сообщений и контекст (session memory)
- **Общее**: все skills, long-term memory, knowledge base, OS integration, системная конфигурация доступны из любого чата
- **Переключение**: `on_chat_switch` hook — сохраняет текущий контекст, загружает контекст целевого чата
- **Удаление**: при удалении чата — его локальные сообщения удаляются, shared memory остаётся
- **Архивирование**: неактивные чаты можно архивировать (освобождает лимит активных)

### 3.4 Model Failover (v3)

Цепочка провайдеров с auto-rotation (Z.ai как основной):

```
Request → Z.ai (primary, OpenAI-compatible)
              │
              ├─ 200 OK → response
              ├─ 429 Rate Limit → wait + retry
              ├─ 500 Error → Yandex Foundation Models (fallback 1)
              │                  ├─ OK → response
              │                  └─ Error → Anthropic Claude (fallback 2)
              │                              ├─ OK → response
              │                              └─ Error → OpenAI GPT (fallback 3)
              │                                          ├─ OK → response
              │                                          └─ Error → Ollama (local fallback)
              └─ Timeout → Ollama (local)
                           └─ response
```

**Auth Profile Rotation**: несколько API-ключей для одного провайдера, автоматическая ротация при rate limit.

**Circuit Breaker**: при N последовательных ошибках провайдера — переключение на следующего в цепочке.

### 5.4 RAG Pipeline

Интеграция через hook `before_prompt_build`:

```
1. User message received in Chat N
       │
       ▼
2. before_prompt_build hook
       │
       ▼
3. Chat context: load Chat N local messages
       │
       ▼
4. Memory query (semantic search via Qdrant) — SHARED across all chats
   ├─ Query: user message embedding (Ollama nomic-embed-text)
   ├─ Top-k=5, similarity > 0.7
   └─ Returns: relevant memories + knowledge chunks
       │
       ▼
5. Inject into system prompt:
   ## Relevant Memory
   - [fact] User prefers dark theme
   - [knowledge] Working on project "osaI"
   - [error] Qdrant timeout → fixed by restart
       │
       ▼
6. Model inference with enriched context
       │
       ▼
7. after_tool_call → extract facts from response
       │
       ▼
8. Store new facts in long-term memory (shared, accessible from any chat)
```

### 5.5 Knowledge Base

- **Ingest**: документ → chunking (1024 tokens, overlap 128) → embedding → Qdrant + SQLite
- **Query**: query → embedding → vector similarity search → rerank → return passages with sources
- **Sources**: add, remove, list по тегам

### 5.6 Embedding Model (v3)

| Провайдер | Модель                 | Размерность | Когда используется                     |
|-----------|------------------------|-------------|----------------------------------------|
| Ollama    | nomic-embed-text       | 768         | **По умолчанию** (локальный)           |
| Yandex    | text-embedding         | 256         | Cloud fallback (Yandex Foundation)     |
| ONNX      | all-MiniLM-L6-v2       | 384         | Offline fallback (Xenova/Transformers.js)|

## 10. Безопасность (Guardrails)

### 10.1 Многоуровневая модель

```
Layer 1: Network (OpenClaw)
├─ WS на localhost (127.0.0.1:18789)
├─ Tailscale для remote access (E2E encryption)
└─ Device pairing verification

Layer 2: Sandbox (OpenClaw)
├─ Docker containers для non-main сессий
├─ Allowlist/denylist для tools
└─ Resource limits (CPU, memory, network)

Layer 3: Permission Prompts (OpenClaw + osaI)
├─ before_tool_call → permission check
├─ Category-based: read=auto, write=confirm, exec=confirm
└─ Desktop notification для permission requests

Layer 4: File Sandbox (osaI)
├─ Allowed dirs: ~/projects, ~/documents, /tmp/osai
├─ Blocked patterns: ~/.ssh/**, ~/.gnupg/**, /etc/**
├─ Symlink resolution
└─ on_file_access hook → audit logging

Layer 5: Shell Security (OpenClaw + osaI)
├─ Blocked commands list
├─ Timeout enforcement (120s)
├─ Command logging
└─ Dangerous pattern detection

Layer 6: Telegram Security (v3)
├─ Bot: allowedUsers whitelist
├─ Userbot: encrypted session storage
├─ Mirror: no sensitive data in TG channels
└─ Audit: all TG interactions logged

Layer 7: Audit (osaI)
├─ All actions logged with trace_id
├─ Permission decisions recorded
├─ Chat context in audit entries
└─ Queryable via API
```

## 14. Примеры сценариев

### Сценарий 1: Мультичаты + Telegram mirror

**Канал**: CLI + Telegram (mirror)
**Чат**: "Проект X"

1. `[CLI]` User: `/chat create "Проект X" --channel cli`
2. `[CLI]` osaI: "Чат 'Проект X' создан."
3. `[CLI]` User: "Настрой TG mirror для этого чата"
4. `[setup]` osaI: "Привяжите Telegram-чат или канал для зеркалирования."
5. `[mirror]` Все сообщения CLI ↔ Telegram "Проект X" синхронизируются
6. `[Telegram]` User (из TG): "Покажи статус деплоя"
7. `[agent]` osaI обрабатывает, отвечает в обоих каналах
8. `[memory]` Факты из этого чата сохраняются в общую долгосрочную память

### Сценарий 2: Z.ai primary + Yandex failover

**Канал**: Telegram bot
**Чат**: Main

1. `[intake]` Message via Telegram bot
2. `[before_model_resolve]` Z.ai (primary)
3. `[model_inference]` Z.ai z-best → 200 OK → response
4. `[later, Z.ai down]` Z.ai → 500 → YandexGPT Pro → 200 OK → response
5. `[audit]` Log: model resolution, provider, tokens, cost

### Сценарий 3: Голосовой ассистент (Voice v3)

**Канал**: CLI
**Чат**: Main

1. `[voice]` User говорит в микрофон (русский)
2. `[STT]` Ollama Whisper → текст: "Найди все дубликаты фото"
3. `[agent]` osaI обрабатывает запрос (Z.ai)
4. `[TTS]` Ollama Piper TTS → аудио ответ
5. `[speaker]` Воспроизведение ответа

### Сценарий 4: Telegram userbot — ожидание ответа

**Канал**: Telegram userbot
**Чат**: Main

1. `[CLI]` User: "Напиши Ивану в Telegram, когда будет готов отчёт"
2. `[agent]` osaI через Telethon отправляет сообщение Ивану
3. `[wait]` osaI ждёт ответ Ивана (через Telethon polling)
4. `[notify]` Иван отвечает → osaI уведомляет через Desktop Notification
5. `[memory]` Факт: "Иван ответил про отчёт" сохраняется в долгосрочную память
6. `[mirror]` Диалог доступен в привязанном TG mirror-чате

### Сценарий 5: Автоматизация файлов через Telegram

**Канал**: Telegram
**Пользователь**: "Найди все дубликаты фото в ~/Downloads и удали"

1. `[intake]` Message received via Telegram
2. `[context_assembly]` Load chat context + relevant memory
3. `[tool: filesystem]` list_dir ~/Downloads --glob "*.jpg" → 150 files
4. `[tool: filesystem]` list_dir ~/Photos --glob "*.jpg" → 200 files
5. `[tool: shell]` md5sum для всех файлов
6. `[agent]` Сравнить хеши → 23 дубликата
7. `[before_tool_call]` Confirm (delete operation)
8. **Telegram**: "Найдено 23 дубликата (450MB). Удалить?" [Да] [Нет]
9. `[tool: filesystem]` delete_file × 23
10. `[after_tool_call]` Audit log + memory store
11. **Telegram**: "Удалено 23 дубликата. Освобождено 450MB."
12. `[desktop_notification]` "osaI: удалено 23 дубликата фото"

### Сценарий 6: Cross-platform (Windows)

**Канал**: CLI (Windows PowerShell)
**Пользователь**: "Покажи загрузку CPU и памяти"

1. `[tool: os-integration]` get_system_info
2. **CLI**: "CPU: 34% | Memory: 8.2/16 GB | Disk: 450/1000 GB"
3. `[desktop_notification]` "osaI: системная информация запрошена"

## 18. Workspace (AGENTS.md, SOUL.md)

### AGENTS.md

```markdown
# osaI Agent

You are osaI, an AI Operating System agent. You execute user intents by using tools and skills.

## Capabilities

- File system management (read, write, search, move, delete)
- Shell command execution (with safety checks)
- Browser automation (navigate, click, fill, screenshot)
- HTTP/API integration
- Desktop OS integration (notifications, processes, file watchers)
- Long-term memory and knowledge base management
- Multi-chat: up to 20 concurrent chats with shared memory
- Multi-channel communication (Telegram bot+userbot, WhatsApp, Discord, Slack, CLI)
- Telegram mirroring (bidirectional sync between osaI chat and TG chat/channel)
- Voice: local-first STT/TTS (Ollama Whisper + Piper) with Yandex fallback

## Rules

- Always confirm before destructive operations (write, delete, execute)
- Stay within sandbox boundaries
- Log all actions for audit
- Ask for clarification when intent is ambiguous
- Remember important facts across sessions and chats
- Use memory and knowledge base to provide better responses
- All chats share long-term memory, skills, knowledge base, and OS integration
```

### SOUL.md

```markdown
# osaI Soul

## Values

- **Helpfulness**: Execute user intents efficiently and completely
- **Honesty**: Report errors and limitations transparently
- **Safety**: Never bypass sandbox or permission checks
- **Privacy**: Keep user data local, never send to third parties
- **Clarity**: Explain what you're doing and why

## Tone

- Concise and direct
- Show progress for multi-step tasks
- Proactively confirm dangerous operations
```

## 21. Компромиссы (Tradeoffs)

### 21.1 Принятые решения

| Решение                          | Альтернатива                   | Обоснование                                                          |
|----------------------------------|--------------------------------|----------------------------------------------------------------------|
| Z.ai primary (не Anthropic)      | Claude как основной            | Z.ai — приоритетный провайдер; OpenAI-совместимый API упрощает       |
| Yandex в цепочке                 | Без Yandex                     | Yandex Foundation даёт LLM + Embeddings + STT/TTS единым провайдером |
| Telethon userbot (Python)        | Только grammY bot              | Telethon — лучший для userbot; работает как microservice             |
| Ollama embeddings default        | OpenAI embeddings              | Local-first; бесплатный; 768-dim достаточно                         |
| TypeScript/Node.js (не Rust)     | Rust — выше производительность | OpenClaw на TS; 80% кода готово; npm ecosystem; кроссплатформенность |
| Fork OpenClaw (не с нуля)        | Custom implementation          | Готовый gateway, agent, 20+ channels, skills; экономия месяцев       |
| SQLite + Qdrant (не Pinecone)    | Pinecone — cloud               | Local-first; Qdrant embedded; SQLite для structured data             |
| SvelteKit (не Next.js)           | Next.js — больше ecosystem     | Легче, быстрее; desktop dashboard не нужен SSR                       |
| pino (не winston)                | Winston — больше formatters    | 6x быстрее; structured JSON                                          |
| Docker sandbox (не firecracker)  | firecracker — безопаснее       | OpenClaw использует Docker; sufficient isolation                     |
| Нативная Windows (не только WSL) | Только WSL                     | Расширение аудитории; node.js кроссплатформенный                     |

### 21.2 Балансы

- **Скорость разработки vs контроль**: В пользу скорости — форк даёт 80% кода, но зависимость от upstream
- **Функциональность vs стабильность**: MVP на стабильном fork; osaI extensions в отдельных пакетах
- **Безопасность vs UX**: Docker + confirmation для write/exec; read — auto в sandbox
- **Стоимость API vs качество**: Z.ai primary, Yandex/Anthropic/GPT fallback, Ollama offline
- **Кроссплатформенность vs сложность**: Нативная Windows + Linux, но через проверенные библиотеки
- **Local-first vs quality voice**: Ollama для STT/TTS по умолчанию, Yandex для лучшего качества
- **Userbot capability vs risk**: Telethon даёт больше возможностей, но риск бана TG
