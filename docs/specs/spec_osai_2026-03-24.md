## 1. Обзор

### 1.1 Цель

Разработать production-ready AI Operating System (osaI) — систему, в которой автономный AI-агент выступает основным интерфейсом между пользователем и компьютером. Система исполняет намерения пользователя (а не просто отвечает текстом), управляет локальными и внешними инструментами, планирует и выполняет многошаговые задачи автономно.

### 1.2 Контекст

Современные AI-ассистенты (ChatGPT, Claude.ai) ограничены чатом — они предлагают текст, но не действуют. Существующие агентные системы (Claude Code, Cursor) ориентированы на разработку ПО. osaI расширяет подход на управление всей системой: файлы, браузер, shell, API, приложения.

### 1.3 Описание решения

Desktop-приложение (Linux/macOS) с архитектурой клиент-сервер:
- **Сервер (daemon)**: Rust-демон `osaid`, выполняющий ядро агента, инструменты, память, observability
- **Клиенты**: CLI (`osai`) и Web dashboard (`osai-ui`), подключающиеся через REST + WebSocket
- **LLM**: Мульти-провайдер — абстракция над Anthropic Claude, OpenAI GPT, локальными моделями (Ollama)
- **Стратегия**: Local-first — все данные и вычисления на машине пользователя

### 1.4 Ключевые принципы

| Принцип | Описание |
|---------|----------|
| Intent execution | Агент действует, а не отвечает текстом |
| Local-first | Данные и ядро — на машине пользователя |
| Tool-first | Все возможности через инструменты (tools) |
| Observable | Каждый шаг агента трейсируется и логируется |
| Secure | Sandbox + подтверждение для разрушительных действий |
| Extensible | Plugin-система для новых инструментов и провайдеров |
| Modular | Чёткое разделение слоёв (core, tools, memory, UI) |

## 3. Ядро агента (Agent Core)

### 3.1 Agent Loop

Агент работает в цикле: **Планирование → Выполнение → Рефлексия → (повтор или завершение)**.

```
┌──────────────────────────────────────────────────────┐
│                    USER INTENT                        │
│              "Переименуй все .jpg в photos/           │
│               по дате съёмки"                         │
└───────────────────────┬──────────────────────────────┘
                        │
                        ▼
              ┌─────────────────┐
              │  Context Builder │
              │  (сбор контекста│
              │   из memory,    │
              │   fs, history)  │
              └────────┬────────┘
                       │
                       ▼
              ┌─────────────────┐
              │     Planner     │
              │  (декомпозиция  │
              │   на подзадачи, │
              │   выбор tools)  │
              └────────┬────────┘
                       │
                       ▼
              ┌─────────────────┐
              │    Executor     │
              │  (вызов tools,  │
              │   запись шагов  │
              │   в trace)      │
              └────────┬────────┘
                       │
                       ▼
              ┌─────────────────┐
              │     Critic      │

```

### 3.2 Компоненты Agent Core

#### Planner

- Декомпозирует намерение пользователя на последовательность шагов
- Для каждого шага выбирает инструмент и формирует параметры
- Вызывает LLM с контекстом (система prompt + история + доступные tools)
- Генерирует structured plan (JSON)

```rust
// Концептуальная структура плана
struct AgentPlan {
    id: Uuid,
    goal: String,
    steps: Vec<PlanStep>,
    created_at: DateTime<Utc>,
}

struct PlanStep {
    id: Uuid,
    description: String,
    tool_name: String,
    tool_params: Value,
    depends_on: Vec<Uuid>,  // зависимости между шагами
    status: StepStatus,      // Pending | Running | Done | Failed
    result: Option<Value>,
}
```

#### Executor

- Выполняет шаги плана последовательно или параллельно (по зависимостям)
- Каждый вызов инструмента оборачивается в span для трейсинга
- Передаёт результат обратно в контекст агента
- Управляет retry-логикой для transient ошибок

```rust
// Retry политика
struct RetryPolicy {
    max_attempts: u32,        // по умолчанию: 3
    backoff: Duration,        // по умолчанию: exponential 1s
    retryable_errors: Vec<String>,  // e.g., "timeout", "rate_limit"
}
```

#### Critic / Validator

- После каждого шага проверяет результат на корректность
- Определяет, достигнута ли глобальная цель
- При ошибке — решает: повторить с тем же подходом, переключить стратегию или запросить помощь пользователя
- Prevents infinite loops: максимальное число итераций (по умолчанию 25)

#### Context Builder

- Формирует промпт для LLM-вызова из:
  - System prompt (роль агента, доступные инструменты)
  - Истории текущей сессии
  - Результатов предыдущих шагов
  - Данных из памяти (RAG-поиск релевантного контекста)
- Управляет размером контекстного окна (обрезка по приоритету)

```rust
struct ContextBuilder {
    max_context_tokens: u32,    // лимит для текущей модели
    system_prompt: String,
    tool_schemas: Vec<ToolSchema>,
}
```

#### Memory Manager

- Краткосрочная память: история текущей сессии (in-memory + SQLite)
- Долгосрочная память: векторные embedding в Qdrant + структурированные записи в SQLite
- Автоматическое извлечение фактов из对话 для долгосрочного хранения
- RAG-поиск по памяти при построении контекста

### 3.3 Single-agent vs Multi-agent

**Текущее решение: Single-agent с заделом на multi-agent**

| Критерий | Single-agent | Multi-agent |
|----------|-------------|-------------|
| Сложность реализации | Низкая | Высокая |
| Отладка | Простая (один поток) | Сложная (пересекающиеся) |
| LLM-затраты | Ниже | Значительно выше |
| Специализация | Через system prompt | Через разные агенты |
| Параллельность | Последовательная | Истинно параллельная |
| На каких задачах нужен multi | — | Комплексные задачи с разными доменами |

**Задел на multi-agent:**
- Каждый "компонент" агента (Planner, Executor, Critic) — отдельный trait
- Trait-объекты позволяют заменять реализации
- В будущем: Coordinator agent, который делегирует задачи специализированным агентам
- Общий Memory Layer позволяет агентам делить контекст

```rust
// Задел: trait-based архитектура
trait Agent {
    async fn execute(&self, task: Task, context: &mut Context) -> Result<AgentOutput>;
}

trait Planner: Send + Sync {
    async fn plan(&self, intent: &str, context: &Context) -> Result<Plan>;
}

trait Executor: Send + Sync {
    async fn execute_step(&self, step: &PlanStep, tools: &ToolRegistry) -> Result<StepResult>;
}

trait Critic: Send + Sync {
    async fn evaluate(&self, plan: &Plan, step: &StepResult) -> Result<CriticDecision>;
}
```

## 4. Система инструментов (Tools)

### 4.1 Контракт инструмента

Каждый инструмент описывается JSON Schema и реализует единый Rust trait:

```rust
#[async_trait]
pub trait Tool: Send + Sync {
    /// Уникальное имя инструмента
    fn name(&self) -> &str;

    /// Человекочитаемое описание (попадает в LLM prompt)
    fn description(&self) -> &str;

    /// JSON Schema параметров
    fn parameters_schema(&self) -> Value;

    /// Выполнение инструмента
    async fn execute(&self, params: Value, ctx: &ToolContext) -> Result<ToolOutput>;

    /// Категория для permission policy
    fn category(&self) -> ToolCategory;
}

pub enum ToolCategory {
    Read,       // чтение данных — auto-approve
    Write,      // запись/модификация — требует подтверждения
    Execute,    // shell-команды — требует подтверждения
    Network,    // HTTP-запросы — требует подтверждения
    System,     // системные операции — всегда подтверждение
}

pub struct ToolOutput {
    pub success: bool,
    pub data: Value,
    pub error: Option<String>,
    pub artifacts: Vec<Artifact>,  // файлы, скриншоты и т.д.
}

pub struct ToolContext {
    pub session_id: Uuid,
    pub user_id: String,
    pub sandbox: Sandbox,
    pub permission_checker: Arc<PermissionChecker>,
    pub memory: Arc<MemoryManager>,
}
```

### 4.2 Реестр инструментов (Tool Registry)

```rust
pub struct ToolRegistry {
    tools: HashMap<String, Arc<dyn Tool>>,
    categories: HashMap<ToolCategory, Vec<String>>,
}

impl ToolRegistry {
    /// Регистрация инструмента
    pub fn register(&mut self, tool: Arc<dyn Tool>);

    /// Получить все схемы для LLM prompt (tool_use)
    pub fn get_tool_schemas(&self) -> Vec<ToolSchema>;

    /// Найти инструмент по имени
    pub fn get(&self, name: &str) -> Option<&Arc<dyn Tool>>;

    /// Получить инструменты по категории
    pub fn get_by_category(&self, category: ToolCategory) -> Vec<&str>;
}
```

### 4.3 MVP-инструменты

#### 4.3.1 File System Tool

```toml
[tool.filesystem]
name = "filesystem"
```

**Sandbox:** Операцит ограничены списком разрешённых директорий (конфигурируется в `osai.toml`). Попытка доступа за пределами — ошибка с объяснением.

- Все команды логируются в audit log

### 8.2 File Sandbox

```rust
pub struct Sandbox {
    allowed_dirs: Vec<PathBuf>,
    blocked_patterns: Vec<glob::Pattern>,
}

impl Sandbox {
    /// Проверяет, допустим ли путь
    pub fn check_path(&self, path: &Path) -> Result<SandboxCheck> {
        let canonical = path.canonicalize()?;
        if self.allowed_dirs.iter().any(|dir| canonical.starts_with(dir)) {
            // Дополнительно проверить blocked patterns
            if self.blocked_patterns.iter().any(|p| p.matches_path(&canonical)) {
                return Err(SandboxError::BlockedPattern(canonical));
            }
            Ok(SandboxCheck::Allowed)
        } else {
            Err(SandboxError::OutsideAllowedDir {
                path: canonical,
                allowed: self.allowed_dirs.clone(),
            })
        }
    }
}
```

## 15. Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| LLM API downtime | Средняя | Высокое | Fallback на Ollama; queue запросов |
| Агент выполняет разрушительное действие | Средняя | Критичное | Sandbox + обязательное подтверждение для write/exec; audit log; undo для файловых операций |
| Контекстное окно недостаточно | Высокая | Среднее | Умная обрезка контекста; summarization старых сообщений; RAG вместо полного контекста |
| Высокая стоимость LLM API | Средняя | Среднее | Token tracking; budget limits в конфиге; fallback на local модели |
| headless_chrome нестабилен | Средняя | Низкое | Retry logic; graceful degradation (tool можно отключить); consider Playwright в будущем |
| Solo developer overload | Высокая | Высокое | Минимальный MVP; модульная архитектура; чёткие приоритеты |
| Rust compile times | Высокая | Низкое | `mold` linker; `sccache`; incremental compilation; workspace split |
| Qdrant embedded stability | Низкая | Среднее | Fallback на sqlite-vec; интерфейс через trait |
| Безопасность sandbox обход | Низкая | Критичное | Честные проверки; не доверять path traversal; запрет symlinks в sandbox |

## 16. Компромиссы (Tradeoffs)

### 16.1 Принятые решения

| Решение | Альтернатива | Обоснование |
|---------|-------------|-------------|
| Rust (не Python/TS) | Python — быстрее prototyping; TS — единый стек | Производительность, безопасность, local-first; AI-библиотеки для Rust уже достаточно зрелые |
| Local-first (не cloud) | Cloud-first — проще масштабировать | Приватность, offline, нет серверных затрат; solo-разработчик не тянет cloud infra |
| Pure Rust UI (не Electron/Tauri) | Tauri — больше экосистема UI-библиотек | Соответствие "pure Rust" философии; меньше зависимостей; egui достаточно для dashboard |
| REST + WS (не gRPC) | gRPC — типобезопаснее, быстрее | Простота дебага; универсальность; WS для streaming компенсирует |
| headless_chrome (не Playwright) | Playwright — кроссбраузерный | Native Rust crate; меньше зависимостей; Chrome-only достаточно для MVP |
| Qdrant embedded (не LanceDB) | LanceDB — проще интеграция | Qdrant более функционален; embedded mode решает проблему зависимостей |
| SQLite (не PostgreSQL) | PostgreSQL — надежнее | Local-first: не нужен отдельный сервер; SQLx SQLite уже с compile-time проверкой |

### 16.2 Балансы

- **Скорость разработки vs качество**: В пользу качества (Rust статически типизирован, но медленнее писать)
- **Функциональность MVP vs сложность**: MVP включает все 4 слоя (agent, tools, memory, observability), но каждый — минимальный
- **Безопасность vs UX**: Sandbox + confirmation для write/exec; read — auto-approve. Можно настроить под себя
- **Стоимость API vs качество**: По умолчанию — Claude (лучшее качество), fallback на Ollama (бесплатно)
